PENM API Documentation

Privacy Enhanced Network Monitor — Full Endpoint Reference

University of Thessaly  |  XTRUST-6G  |  Version 1.0  |  2025

The PENM API provides seven endpoints covering four functional areas: aggregated network traffic statistics, IP role snapshots, raw packet capture retrieval, IP role profiling, and active network probing. All endpoints require Bearer Token authentication and are accessible via the integrated Swagger UI at /apidocs.

Text-based telemetry (network statistics and role snapshots) is returned in CSV format by default, using Zeek naming conventions and Unix Epoch timestamps, to ensure compatibility with SIEMs, Grafana, and data lake ingestion pipelines. A format=json query parameter switches these endpoints to JSON output. Binary PCAP responses use the standard application/vnd.tcpdump.pcap content type.

Authentication

All requests must include the Authorization header with a valid JWT obtained from POST /auth/login. 

Authorization: Bearer <YOUR_ACCESS_TOKEN>

Rate Limits

Endpoints 1–4 (monitoring and PCAP retrieval) share the global limit of 300 requests per minute. The profiling endpoint (5) is limited to 10 requests per minute due to its CPU-intensive processing. The active probing endpoints (6–7) are limited to 5 requests per minute for the dispatch call. Clients should implement exponential back-off when HTTP 429 is received.

Timestamps & Formats

  • Timestamps: All time-based parameters and response fields use Unix Epoch time (e.g., 1708426800.000000).
  • Default format: text/csv using Zeek field naming conventions for endpoints 1 and 2.
  • JSON format: Pass format=json to receive application/json instead of CSV.

Endpoint Details

1. Get Network Statistics

Retrieve aggregated network traffic statistics within a specified timeframe. Records are drawn from the flow_statistics TimescaleDB hypertable, which is continuously populated by the Sensor VM's Zeek agent. The response includes per-flow originator and responder byte and packet counts mapped to Zeek's conn.log field naming conventions.

GET /v1/network/statistics

Default Content-Type: text/csv

Query Parameters:

ParameterTypeRequiredDescription
start_timeFloatNo Unix Epoch start of the query window (default: 0, i.e., all records).
end_timeFloatNo Unix Epoch end of the query window (default: current UTC time).
limitIntegerNo Maximum number of rows to return. Range: 1–10 000. Default: 1000.
formatStringNo Response format. "csv" (default) or "json".

Response Fields (Zeek-aligned):

  • ts: Flow timestamp (Unix Epoch float).
  • id.orig_h: Source IP address.
  • id.resp_h: Destination IP address.
  • proto: Transport protocol (e.g., tcp, udp, icmp).
  • conn_state: Connection state matching Zeek definitions (e.g., S0, SF, REJ).
  • orig_bytes: Total payload bytes sent by the originator.
  • resp_bytes: Total payload bytes sent by the responder.
  • orig_pkts: Total packets sent by the originator.
  • resp_pkts: Total packets sent by the responder.
Example Request
GET /v1/network/statistics?start_time=1708387200.0&end_time=1708473600.0&limit=500
Authorization: Bearer <TOKEN>

2. Get Latest Role Snapshot

Retrieve the most recent classification of IP addresses and their assigned functional roles. Role snapshots are generated periodically by the 8-hour background scheduler or triggered manually. Each record includes the ML/heuristic confidence score and a human-readable reasoning string describing the evidence used for the classification.

GET /v1/network/roles/latest

Default Content-Type: text/csv

Query Parameters:

ParameterTypeRequiredDescription
limitIntegerNo Maximum number of IP records to return. Range: 1–10 000. Default: 1000.
formatStringNo Response format. "csv" (default) or "json".

Response Fields:

  • ts: Unix Epoch timestamp of snapshot generation.
  • id.orig_h: The IP address being evaluated.
  • role: Assigned functional role (e.g., gNB, AMF, UPF, UE, NEAR_RT_RIC).
  • confidence: Classification confidence score, 0.0–1.0.
  • reasoning: Brief explanation of how the role was determined (e.g., "Identified via NGAP Code 21").
Example Request
GET /v1/network/roles/latest?limit=100
Authorization: Bearer <TOKEN>

3. Get Timeframe PCAP (Headers Only)

Provides a binary .pcap file for a specific timeframe. The Sensor VM applies a snapshot length (snaplen) truncation so that each packet contains only its Ethernet, IP, and TCP/UDP headers — stripping the application payload. This reduces bandwidth and accelerates downstream flow analysis while preserving all metadata required for traffic classification.

GET /v1/network/pcap/headers

Response Content-Type: application/vnd.tcpdump.pcap

Query Parameters:

ParameterTypeRequiredDescription
start_timeFloatYes Unix Epoch timestamp for the start of the capture window.
end_timeFloatYes Unix Epoch timestamp for the end of the capture window.

Response: A downloadable binary .pcap file containing header-only packets for the requested timeframe. The filename is headers_<start_time_int>.pcap.

Example Request
GET /v1/network/pcap/headers?start_time=1708387200.0&end_time=1708473600.0
Authorization: Bearer <TOKEN>

4. Get Full Payload PCAP (Latest Snapshot)

Provides the complete binary .pcap file representing the most recent capture snapshot held by the Sensor VM. Unlike Endpoint 3, this file contains full application payloads for deep packet inspection. The file is streamed directly from the Sensor VM's ring-buffer storage to the caller without intermediate buffering on the application server.

GET /v1/network/pcap/latest/full

Response Content-Type: application/vnd.tcpdump.pcap

Query Parameters: None.

Response: A downloadable binary .pcap file containing the complete latest snapshot from the Sensor VM ring buffer.

Note: While there are no enforced rate limits on this endpoint beyond the global 300 req/min, the file size may be up to 500 MB (one ring-buffer segment). Clients should implement back-off strategies and process the response as a stream to avoid memory exhaustion.
Example Request
GET /v1/network/pcap/latest/full
Authorization: Bearer <TOKEN>

5. IP Role Profiling (Full Pipeline)

Executes the complete rule-based IP role classification pipeline against a previously uploaded or captured PCAP file. The pipeline extracts per-flow features using TShark, identifies network function signatures (e.g., AMF NGAP exchanges, UPF GTP-U traffic, RRC signalling indicative of a gNB), and assigns a functional 5G/O-RAN role and confidence score to each IP endpoint observed in the capture.

The optional selected_ips filter restricts analysis to a specific subset of endpoints, which is useful when chaining this endpoint after the Agglomerative Clustering pipeline to profile only the IPs belonging to a cluster of interest.

POST /run_pipeline

Content-Type: application/json

Response Content-Type: application/json

Rate Limit: 10 requests per minute per user

Request Body Parameters:

ParameterTypeRequiredDescription
pcap_file_pathStringYes Filename of the target PCAP as returned by the upload or real-time capture endpoints (e.g., 20250601_capture.pcap). The caller must own the file; a 403 is returned otherwise.
model_nameStringYes Classification model identifier. Pass the base filename without extension, or "rule_based" as a generic fallback.
selected_ipsArray<String>No Optional list of IP addresses to restrict analysis to. When omitted, all IPs in the PCAP are profiled. When provided, only the specified addresses are classified.

JSON Response Fields:

  • status: "success" or "failed".
  • total_classified: Integer count of IP addresses that received a role assignment.
  • processing_time: Pipeline wall-clock time in seconds (float).
  • ip_roles: Object mapping each IP address to a classification object containing:
    • role: Assigned functional role string (e.g., "AMF", "UPF", "gNB", "UE", "NEAR_RT_RIC", "Unidentified").
    • confidence: Classification confidence score, 0.0–1.0.
  • rule_based_classification_summary: Array of role summary objects, each with:
    • class_name: Role label string.
    • count: Number of IPs assigned this role.
    • ips: Array of IP address strings assigned this role.
Note: The pipeline runs in a separate OS process with a 600-second timeout to prevent large captures from blocking the API worker. For captures with a very high number of unique IP endpoints, processing time may approach this limit.
Example Request
POST /run_pipeline
Authorization: Bearer <TOKEN>
Content-Type: application/json

{
  "pcap_file_path": "20250601120000_testbed.pcap",
  "model_name":     "20250601120000_testbed",
  "selected_ips":   ["10.45.0.1", "10.45.0.2", "10.45.0.5"]
}
Example Response (200 OK)
{
  "status": "success",
  "total_classified": 3,
  "processing_time": 4.71,
  "ip_roles": {
    "10.45.0.1": { "role": "AMF",  "confidence": 0.90 },
    "10.45.0.2": { "role": "UPF",  "confidence": 0.90 },
    "10.45.0.5": { "role": "gNB",  "confidence": 0.90 }
  },
  "rule_based_classification_summary": [
    { "class_name": "AMF", "count": 1, "ips": ["10.45.0.1"] },
    { "class_name": "UPF", "count": 1, "ips": ["10.45.0.2"] },
    { "class_name": "gNB", "count": 1, "ips": ["10.45.0.5"] }
  ]
}

6. Active Probing — Dispatch Nmap Scan

Dispatches an asynchronous Nmap scan from the Sensor VM against one or more target IP addresses or CIDR ranges. The endpoint validates all input parameters against a strict allowlist (valid IPv4, CIDR, plain hostnames) before forwarding to the Sensor VM. The scan runs asynchronously and the request returns immediately with an acceptance acknowledgement. Results are retrieved via Endpoint 7.

Three scan profiles are available: fast (Nmap -F, 100 common ports), deep (Nmap -sV, service and version detection across all open ports — default), and vuln (version detection combined with the Vulners NSE script across 10,000 ports, producing known CVE identifiers per open service).

POST /v1/scan/start

Content-Type: application/json

Response Content-Type: application/json

Rate Limit: 5 requests per minute per user

Request Body Parameters:

ParameterTypeRequiredDescription
targetStringConditional Single scan target: IPv4 address, CIDR range, or hostname (e.g., "10.45.0.0/24"). Exactly one of target or targets must be present.
targetsArray<String>Conditional List of individual IP addresses to scan (e.g., the keys from an ip_roles profiling response). Exactly one of target or targets must be present.
profileStringNo Scan profile: "fast", "deep" (default), or "vuln".
Security: All string values are validated server-side against a strict allowlist before being forwarded to the Sensor VM. Values containing shell metacharacters or invalid patterns are rejected with HTTP 400.

Response Fields (202 Accepted):

  • status: Acknowledgement string (e.g., "accepted").
  • message: Human-readable confirmation that the scan was dispatched.
Example Request — single CIDR target
POST /v1/scan/start
Authorization: Bearer <TOKEN>
Content-Type: application/json

{
  "target":  "10.45.0.0/24",
  "profile": "deep"
}
Example Request — multi-IP list from profiling output
POST /v1/scan/start
Authorization: Bearer <TOKEN>
Content-Type: application/json

{
  "targets": ["10.45.0.1", "10.45.0.2", "10.45.0.5"],
  "profile": "vuln"
}
Example Response (202 Accepted)
{
  "status":  "accepted",
  "message": "Nmap scan started."
}

7. Active Probing — Poll Scan Results

Retrieves the current status and, upon completion, the full results of the most recently dispatched Nmap scan from the Sensor VM. Poll this endpoint at regular intervals (recommended: every 5 seconds) after calling Endpoint 6, until status is "completed" or "error". No scan-specific identifier is needed; the Sensor VM maintains a single active scan slot and always returns the result of the most recent job.

GET /v1/scan/results

Response Content-Type: application/json

Query Parameters: None.

Response Fields (200 OK):

  • status: Current state of the Nmap job:
    • "idle" — No scan has been dispatched yet.
    • "running" — Scan in progress; poll again shortly.
    • "completed" — Scan finished; results array is populated.
    • "error" — Scan failed; inspect message.
  • message: Human-readable status or error description.
  • results: Array of host objects (present when "completed"), each containing:
    • host: IP address of the scanned host.
    • hostname: Resolved hostname, if available.
    • state: Host reachability (e.g., "up").
    • ports: Array of open port objects, each with:
      • port: Port number (integer).
      • protocol: Transport protocol ("tcp" / "udp" / "sctp").
      • state: Port state (e.g., "open").
      • service: Service name as identified by Nmap.
      • version: Service version string (populated for "deep" and "vuln" profiles).
      • cves: Array of CVE identifier strings (populated only for "vuln" profile).
Polling guidance: A deep scan against a /24 subnet typically completes within 2–5 minutes. A vulnerability scan may take up to 15 minutes depending on the number of open services discovered.
Example Request
GET /v1/scan/results
Authorization: Bearer <TOKEN>
Example Response — scan completed (deep profile)
{
  "status":  "completed",
  "message": "Scan completed successfully.",
  "results": [
    {
      "host":     "10.45.0.1",
      "hostname": "amf.core.local",
      "state":    "up",
      "ports": [
        { "port": 38412, "protocol": "sctp", "state": "open",
          "service": "ngap",  "version": "Open5GS AMF 2.6.4", "cves": [] },
        { "port": 7777,  "protocol": "tcp",  "state": "open",
          "service": "sbi",   "version": "Open5GS HTTP/2 SBI",  "cves": [] }
      ]
    },
    {
      "host":     "10.45.0.2",
      "hostname": "upf.core.local",
      "state":    "up",
      "ports": [
        { "port": 2152, "protocol": "udp", "state": "open",
          "service": "gtp-user", "version": "Open5GS UPF 2.6.4", "cves": [] }
      ]
    }
  ]
}
