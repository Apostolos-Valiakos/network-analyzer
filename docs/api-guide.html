API Guide

Using the PENM API

For partners and developers who call PENM from scripts or tools. The interactive documentation at /apidocs on your server has every parameter and response schema; this guide explains how to use it.

1. Basics

Base URLhttp://<server-ip>:5555 (your administrator gives you the address and, if needed, VPN access)
Interactive docshttp://<server-ip>:5555/apidocs, open without login
AuthenticationA login token in the Authorization: Bearer <token> header. Tokens last 8 hours
AccountsCreated by a PENM administrator. Keep your password and tokens out of shared scripts and repositories

2. Logging in

curl -s -X POST http://<server-ip>:5555/auth/login \
     -H "Content-Type: application/json" \
     -d '{"username": "YOUR_USERNAME", "password": "YOUR_PASSWORD"}'
# → {"access_token": "eyJhbGciOi...", "is_admin": false}

At most 10 login attempts per minute. A token can also be copied from the web application: after logging in, the browser's developer tools (F12) show it under Application → Local Storage → auth_token.

3. Interactive docs (/apidocs)

  1. Open /apidocs and click Authorize.
  2. In Value, enter the word Bearer, one space, then the token: Bearer eyJhbGciOi…. The word is required.
  3. Click Authorize inside the dialog, then Close. The padlocks close.
  4. Expand an endpoint, Try it out, fill in the parameters, Execute. The curl command shown must contain -H "Authorization: Bearer …".

Reloading the page forgets the authorization; authorize again.

4. From scripts

TOKEN=eyJhbGciOi...
curl -s -H "Authorization: Bearer $TOKEN" "http://<server-ip>:5555/v1/network/statistics?format=json&limit=100"
import getpass, requests

BASE = "http://<server-ip>:5555"
login = requests.post(f"{BASE}/auth/login", timeout=10, json={
    "username": "YOUR_USERNAME", "password": getpass.getpass("PENM password: ")})
login.raise_for_status()
headers = {"Authorization": f"Bearer {login.json()['access_token']}"}

flows = requests.get(f"{BASE}/v1/network/statistics", headers=headers, timeout=30,
                     params={"format": "json", "limit": 100}).json()

5. Endpoints

All need a login token unless stated otherwise. Times are Unix timestamps in seconds (UTC); format is json or csv (default csv).

Continuous monitoring

EndpointReturnsParameters
GET /v1/network/statisticsFlow records (Zeek fields: ts, id.orig_h, proto, bytes, packets, connection state…), newest firststart_time (default 0), end_time (default now), limit 1–10000 (default 1000), format
GET /v1/network/exportThe same flows for bulk export, as a downloadstart_time, end_time, limit (omit for all), format
GET /v1/network/roles/latestThe latest live role snapshot: one row per IP with role, confidence, reasoning and source. Two sources: pcap (the backend analyses the sensor's latest slice, every 5 minutes by default) and dpi (the sensor's live DPI, every minute). Without source, the DPI snapshot while it is no older than 3 minutes, otherwise the pcap onelimit, format, source
GET /v1/network/pcap/latest/fullThe sensor's most recent capture file, full payloads (.pcap), up to about an hour of traffic—
GET /v1/network/pcap/headersThe traffic in a time window, packet headers onlystart_time, end_time (required)
POST /v1/analyze_liveRole analysis of the latest live snapshot (5 per minute)—

Captures are only kept for a limited time on the sensor (typically 6–24 hours). Example, the last 10 minutes:

END=$(date +%s); START=$((END - 600))
curl -s -H "Authorization: Bearer $TOKEN" -o last10min.pcap \
     "http://<server-ip>:5555/v1/network/pcap/headers?start_time=$START&end_time=$END"

Nmap scans

EndpointNotes
POST /v1/scan/startBody: exactly one of "target" (address, range or host name) or "targets" (list of addresses), and "profile": fast (100 common ports), deep (service versions) or vuln (versions + known vulnerabilities, slowest). 202 when accepted; 5 per minute
GET /v1/scan/resultsstatus: running (poll again in ~5 s), completed (results included), error (see message), idle
curl -s -X POST http://<server-ip>:5555/v1/scan/start -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" -d '{"target": "<address>", "profile": "fast"}'
curl -s -H "Authorization: Bearer $TOKEN" http://<server-ip>:5555/v1/scan/results

Only scan networks you are authorised to test. There is one scan slot for all users: a new scan replaces the previous results.

Captures and analysis

EndpointNotes
POST /automated-analysisUpload a .pcap (multipart field file): stores it and returns packet count, graph, roles and privacy records. 5 per minute
GET /analyze-saved-pcap/{filename}Packet count, conversation graph and per-IP protocol stacks (e.g. sctp:ngap:nas-5gs) of a stored capture
POST /run_pipelineRole assessment of a stored capture, with confidence and reasoning; optional selected_ips. 10 per minute
GET /save_roles?file=&type=json|csvRole summary download
GET /suggested_clusters?file=, POST /clusteringSuggested cluster count; agglomerative clustering with anomaly flags (10 per minute)
POST /save-results, GET /clustering-output/{filename}Save and download clustering results
GET /privacy-records/{filename}, POST /privacy-metricsPer-host privacy records; privacy metrics with optional anonymisation
POST /save-pcap, GET /generated_pcaps/{filename}Upload base64 packets in chunks to build a capture (30 per minute); download a capture
POST /start-analysis-from-websocketThe server captures from a sensor's packet stream for seconds (1–3600), saves the capture for you and analyses it. 202 at once; the outcome arrives on that WebSocket and in History

You can only access your own files; admins can access all.

History, users, internal

GET /v1/history/pcaps, /generated, /clustersYour uploads, generated captures, clustering results
GET /v1/history/pcap/{id}/result, /cluster/{id}/resultStored result
POST /v1/history/pcap/{id}/reanalyze, DELETE /v1/history/pcap/{id}, DELETE /v1/history/cluster/{id}Re-run (5 per minute) and delete

POST /v1/ingest/zeekInternal: the sensor posts flows with the X-Internal-Token header, not a login token
POST /v1/ingest/dpiInternal: the sensor's live DPI agent posts one window of role evidence (no subscriber data), with the same header
POST /v1/ingest/hubbleInternal: the sensor's Hubble agent (or, without Hubble, its Kubernetes API agent with "source": "k8s-api") posts which pod or Service owned which IP, and flows per minute, with the same header

6. Live events (Socket.IO)

The backend pushes events over Socket.IO at the base URL:

EventPayload
new_network_dataEach batch of new flow records, as soon as the sensor sends it
network_alert{level, title, message} for a single flow over 5 MB ("Massive Data Transfer"), over 5,000 packets ("Packet Flood Detected") or rejected ("Connection Rejected")

7. Formats, warnings, limits

  • Timestamps: Unix seconds, UTC.
  • Partial results: when part of a request fails but the rest succeeds, the response is still 200 and carries "warnings": [ … ] with readable messages. The key is absent when nothing went wrong.
  • Rate limits: per client address, as listed above; over the limit you get 429.
  • Unused parameters: model_name is accepted and ignored; roles always come from the rule engine.

8. Errors

ResponseMeaning
401 "Missing Authorization Header"No token sent (in /apidocs: not authorized, or the page was reloaded)
401 "Missing 'Bearer' type …"The word Bearer is missing before the token
401 "Token has expired"Log in again (tokens last 8 hours)
403 / 404Not your file, or no such file
400A parameter is missing or invalid; the message says which
429Rate limit reached; wait a minute
500Server error; details are in the server log
502 / 503 / 504The capture sensor did not answer, cannot be reached, or timed out
